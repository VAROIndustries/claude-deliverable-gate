# Deliverable Gate

A Claude Code plugin that answers one question before client work leaves your workspace:

> **Exactly what will be published, where will it go, and what checks have passed?**

You configure a deliverable: source, allowlist, exclusions, destination, audience and required checks. The
gate then builds an **isolated candidate snapshot** from the commit, writes a **hashed manifest**, runs every
check **against that candidate** (not your working tree), and shows you a report. Nothing is published unless
you explicitly approve **that candidate for that destination**. If anything changes afterwards (snapshot
bytes, policy, destination, the destination branch, the gh account), the approval is void.

It is **report-only by default** and has exactly one publisher: a GitHub snapshot push.

Passing checks reduce risk. They are **not** a guarantee that a deliverable contains no confidential
information.

```
| Check       | Required | Result         | Summary                                                        |
| paths       | yes      | PASS           | 7 files, all inside the allowlist ...                          |
| secrets     | yes      | PASS           | gitleaks 8.30.1 (default rules, candidate ignores disregarded) |
| links       | yes      | FAIL           | 1 of 4 relative link(s)/image(s) broken                        |
| provenance  | yes      | FAIL           | stale: input docs/handover-guide.md changed since generation   |
| binaries    | yes      | INCOMPLETE     | 2 binary file(s) were not inspected ...                        |
| destination | yes      | PASS           | example-client-org/portal-handover is private, pushable by ... |
```

A full sample is in [`examples/sample/report.md`](examples/sample/report.md) and
[`examples/sample/manifest.json`](examples/sample/manifest.json), generated by `node examples/demo.js` from
synthetic data.

## Install

Requirements: Node 20+, Git, the [GitHub CLI](https://cli.github.com/) (`gh`) logged in as your publishing
account, and [gitleaks](https://github.com/gitleaks/gitleaks) 8.19+ for the secrets check. Without gitleaks, the
secrets check reports **INCOMPLETE** and never PASS.

```
winget install Gitleaks.Gitleaks
```

In Claude Code:

```
/plugin marketplace add VAROIndustries/claude-deliverable-gate
/plugin install deliverable-gate@deliverable-gate
```

If gitleaks isn't on `PATH`, set `DELIVERABLE_GATE_GITLEAKS` to the executable.

## Workflow

Ask Claude ("what would we publish for the portal handover?"), or run the CLI yourself:

```
node gate.js init portal-handover --repo C:/Work/example-portal
node gate.js check portal-handover
node gate.js approve portal-handover --candidate 20261018-161243-bacf --destination "github:example-client-org/portal-handover@main (private, as your-publishing-account)"
node gate.js publish portal-handover --candidate 20261018-161243-bacf
```

| Command | Effect |
| --- | --- |
| `init <name> --repo <path>` | Writes a policy skeleton to `~/.claude/deliverable-gate/deliverables/<name>/policy.json`. Nothing in the repo is touched. |
| `check <name>` | Builds a new candidate, writes `manifest.json`, `report.json` and `report.md`, prints the report. Exit 0 READY, 2 INCOMPLETE, 1 BLOCKED. |
| `approve <name> --candidate <id> --destination "<identity>" [--accept-incomplete a,b]` | Records an approval bound to the candidate hash, policy hash, destination identity and destination branch head. You must restate the destination. FAIL can't be approved, and each INCOMPLETE required check must be accepted by name. |
| `publish <name> --candidate <id>` | Re-verifies everything, then pushes the snapshot as one commit. |
| `status [<name>]` | Candidates, verdicts, approvals (marked INVALID with the reason) and publication log. |
| `verify <name> --candidate <id>` | Re-hashes a snapshot against its manifest. |
| `clean <name> [--keep N] [--all]` | Retention. Keeps the newest N candidates (default 3) plus the latest approved one, which is the diff baseline. `--all` keeps only the policy and publication log. |

The Claude skill wraps the same commands. It never runs `approve` or `publish` without your explicit
instruction in the conversation.

## Policy

See [`examples/policy.example.json`](examples/policy.example.json). Policies live in
`~/.claude/deliverable-gate/` (or `DELIVERABLE_GATE_HOME`), never in the client repository.

| Field | Meaning |
| --- | --- |
| `source.repo`, `source.revision` | Git repository and the commit to snapshot (default `HEAD`). |
| `source.base` | Optional subdirectory; candidate paths are relative to it. |
| `source.worktreePaths` | Globs taken from the working tree instead of the commit, for uncommitted generated output. Explicit opt-in. |
| `include` | **Allowlist.** Required. Anything not matched is excluded ("not in allowlist"). |
| `exclude` | `{glob, reason}`. The reason appears in the report. |
| `allowedExtensions` | Optional file-type allowlist (`""` = no extension). Without it, archives and executables FAIL. |
| `destination` | `type: "github"`, `owner`, `repo`, `branch`, `visibility`, `account` (gh login that must be active), optional `commitIdentity`. |
| `requiredChecks` | Checks that must PASS (or be explicitly accepted if INCOMPLETE). Others are shown as advisory. Default: all. |
| `sensitive.patterns` / `sensitive.paths` | Client-specific regexes (codenames, hostnames) and path globs. |
| `sensitive.allow` | Waivers `{rule, glob, reason}`. Listed in every report. |
| `provenance` | `{output, inputs[], record}` rules for generated documents (below). |

Globs support `**`, `*` and `?` and match case-insensitively, so an exclusion can't be dodged by case. Any
policy change invalidates existing approvals.

## Checks

Each check reports **PASS**, **FAIL** or **INCOMPLETE**. INCOMPLETE means "not checked", never "safe".

| Check | What it does |
| --- | --- |
| `paths` | Allowlist and exclusions. Traversal segments, absolute paths, `.git` segments, Windows reserved names, case collisions, files over 100 MiB. Symlinks (committed or in the worktree, including junctions): an escape from the source root FAILs, and internal links FAIL too because they're not published. Submodules. Unexpected file types. |
| `secrets` | Runs **gitleaks** (`gitleaks dir`) on the snapshot with a pinned config. A candidate-supplied `.gitleaks.toml` and `gitleaks:allow` comments are ignored (tested), and the ignore-file path is pinned to the gate's own scan folder, so the deliverable can't silence its own scan. A missing scanner or scanner error is INCOMPLETE. Only file, line and rule id are kept, never the match. |
| `sensitive` | Built-in rules for correspondence (`.eml`/`.msg`/`.mbox`/`.pst`, `correspondence/`, email headers in text files), session logs and transcripts, local settings (`.env`, `*.local.json`, keys, `.npmrc`…; `.env.example` is allowed) and private sample data (`sample-data/`, `private/`, `*.db`, dumps). Also your patterns and path rules. Reports file:line and rule id only. |
| `links` | Relative Markdown links, reference definitions and `<img>`/`<a>` targets must resolve **inside the candidate**. Catches missing targets, case mismatches (broken on case-sensitive hosts), links leaving the deliverable and links to excluded files. Code blocks are skipped. |
| `provenance` | For each rule, the output must be in the candidate, and the build record (`{output:{sha256}, inputs:{path: sha256}}`, written by your build) must describe *this* output and the *current* inputs. A changed input is stale (FAIL). A missing record, or an input the record doesn't cover, is INCOMPLETE. **Timestamps are never used.** No rules configured is INCOMPLETE. |
| `binaries` | Binary files are listed as **uninspected** (INCOMPLETE), because the text-based checks can't see inside them. |
| `lfs` | Unresolved Git LFS pointers FAIL, and the report says whether the object exists in the local LFS store or is unavailable. The publisher uploads no LFS objects, so recipients would get the pointer. `.gitattributes` declaring LFS filters also FAILs. |
| `destination` | Via `gh`: the active account equals `account`. The repository exists (it is never created), has the expected owner (renames and transfers are detected) and visibility (never changed), and is pushable and not archived. Also reads the branch head that the approval binds to. |
| `history` | `snapshot` mode PASSes with a statement of what is pushed. `history` mode is **refused**. |

### Snapshot vs history publication

A clean working tree says nothing about what's reachable in Git history: a secret committed and later
deleted is still in every clone. This version therefore only publishes **snapshots**. The destination gets a
single new commit whose tree is exactly the manifest, parented on the destination's own branch head. No
source commits, tags, refs or objects are pushed. The test suite proves this by publishing from a repository
whose history contains a synthetic secret, then checking that no object in the destination contains it.
Publishing history (outgoing commit and blob inspection) is not supported, and a `history` policy is
refused.

## Boundaries: enforced vs advisory

| Boundary | Status |
| --- | --- |
| Source files are never modified, cleaned or rewritten; nothing is written into the source repo | **Enforced.** The gate only reads (`git ls-tree`, `cat-file`, `status`) and writes under its own home. Tested. |
| The candidate excludes unrelated working-tree changes | **Enforced.** Content comes from the pinned commit; only `worktreePaths` you opt into come from disk. The report lists what was left out. |
| Published bytes = approved bytes | **Enforced.** The snapshot is re-hashed before approval and again before publish. The commit is built with Git plumbing (`hash-object --no-filters`, `mktree`, `commit-tree`) directly from the snapshot, so line-ending conversion, LFS filters, `.gitattributes` and commit hooks can't change it. The tree is compared with the manifest before pushing. |
| Approval is bound to candidate + destination + policy + destination head | **Enforced** by the gate's own publish path. Tested for content mutation, an added file, a policy change, a destination change, an identity drift and a third-party push after approval. |
| No force push, no history rewrite, no visibility or account changes | **Enforced** in the publisher: a plain push of one commit; a non-fast-forward is rejected by the server. |
| The pushing credential is the verified gh account | **Enforced** for the gate's push: Git is run with `credential.helper=!gh auth git-credential`, so the account the check verified is the one that authenticates. |
| A human, not Claude, approved | **Advisory.** The CLI can't tell who typed `approve`. The skill tells Claude to approve only on your explicit instruction, and `--destination` must be restated. Review approvals with `status`. |
| Nobody pushes the source repo directly | **Advisory.** A `PreToolUse` hook denies Claude's own `git push` / `gh repo create|edit|sync` / `gh release create` from or naming a registered source repo. It can't see other terminals, aliases, scripts, IDE Git or anything outside Claude's tool calls. |
| The snapshot can't be edited between approval and publish | **Detected, not prevented.** Snapshot files are read-only, but anyone with your file permissions can change them. Any change is caught by re-hashing, and publish refuses. |
| Anything the destination does after the push (forks, mirrors, CI, collaborators) | **Out of scope.** |
| Absence of confidential information | **Not guaranteed.** Checks are pattern-based. Binaries are uninspected, and a scanner that misses a secret still reports PASS for what it saw. |

## Data, retention, cleanup

- All state lives in `~/.claude/deliverable-gate/` (set `DELIVERABLE_GATE_HOME` to move it). It's outside
  every Git repository and outside the plugin directory, so it survives plugin updates.
- Candidates hold a full copy of the deliverable. Nothing is deleted automatically. Use
  `gate.js clean <name>` (keeps the newest 3 plus the latest approved) or `--all`. To remove everything,
  delete the deliverable's folder.
- `publications.jsonl` records each publication: candidate hash, approval hash, commit and destination.
- Reports contain file paths, sizes, hashes, rule ids and line numbers, never matched contents. Treat them as
  local client data anyway.

## Integrations

- **Identity Guard** (optional): if installed, `publish` runs its documented CLI
  (`idguard.mjs check -- git push <url> <branch>`). A MISMATCH refuses the publish. UNKNOWN or not installed
  is reported, and the gate's own destination check still applies.
- **CopilotHud**: no integration. It keeps its state inside VS Code and exposes no supported interface.
- **NoteSmith / KnotDo**: nothing is synced automatically. Ask Claude to file a summary or tasks; the skill
  limits these to file names and rule ids.

## Tests

```
node --test test.js
```

All fixtures are synthetic and generated at runtime, including the secrets, which are assembled at runtime
so this repository contains none. "Publishing" targets a temporary local bare repository with a stubbed `gh`.
No test reaches GitHub. They cover: allowlist escapes, committed and worktree symlinks/junctions, case
collisions, excluded correspondence, sensitive content not echoed, synthetic secrets with a candidate-supplied
config and allow-comment, missing scanner, broken links, stale/missing/unrecorded generated documents, unsupported
binaries, LFS pointers, history mode, sensitive history not reaching the destination, destination identity
mismatch, destination change, candidate mutation after approval, a third-party push after approval, and the
advisory hook. The gitleaks test is reported as skipped, not passed, when gitleaks isn't installed.
